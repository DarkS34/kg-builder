# kg-builder

Build a **typed knowledge graph** out of a folder of documents (`.pdf`, `.docx`, `.md`, `.txt`), using **local LLMs** through [Ollama](https://ollama.com). No external API, no graph database, no agent framework — the output is plain JSON.

The distinguishing feature: **the relation vocabulary is data, not code**. The four default relations (`prerequisite`, `is_a`, `part_of`, `related_to`) are a *default*, not an assumption baked into the prompts. Declare a different set — three relations, or twelve, for medicine, law, or software — and every prompt, every validator and the output schema follow automatically. You never edit a prompt.

The tool is language-agnostic: prompts and documentation are in English, but **extraction preserves the source language**. A Spanish corpus yields Spanish concept names and Spanish domain names; only the relation keys stay fixed, because they are identifiers you chose.

---

## Install

```bash
git clone <your-repo-url> kg-builder
cd kg-builder
uv sync          # or: pip install -e .
```

You need Ollama running and the models pulled. `kg-builder` pulls and warms them for you on first run:

```bash
ollama serve                      # default host: localhost:11434
export OLLAMA_HOST=localhost:11434   # only if yours differs
```

## Quickstart

```bash
# 1. see exactly what the model will be told about your relations
uv run kg-builder relations

# 2. full pipeline over ./corpus, writing to ./output
uv run kg-builder all corpus

# or one stage at a time
uv run kg-builder build  corpus            # -> output/knowledge_graph_partial.json
uv run kg-builder clean                    # -> output/knowledge_graph_cleaned.json
uv run kg-builder curate                   # -> output/knowledge_graph_autogenerated.json
```

With a different relation vocabulary — nothing else changes:

```bash
uv run kg-builder --relations es all corpus                        # built-in Spanish schema
uv run kg-builder --relations examples/spanish_relations.json all corpus   # or your own JSON
```

`python -m kg_builder ...` works identically if you'd rather not install the script.

## The pipeline

Three stages, each resumable and each writing a file you can inspect and hand-edit before running the next one.

```
corpus/*.pdf|docx|md|txt
        │
        │  build     per-chunk extraction + one global linking pass
        ▼
knowledge_graph_partial.json          flat: entities / edges / relations
        │
        │  clean     deterministic merge + LLM alias mapping + noise removal
        ▼
knowledge_graph_cleaned.json          flat, deduplicated
        │
        │  curate    domain grouping, relation bucketing, cycle breaking
        ▼
knowledge_graph_autogenerated.json    curated schema — A DRAFT
        │
        │  manual review  ← this step is yours
        ▼
knowledge_graph.json
```

**`build`** converts each document to markdown (via [Docling](https://github.com/docling-project/docling)), splits it into chunks, and asks the model for concepts plus triples **already typed** against your schema. Triples that are self-loops, use an unknown type, or point at a concept that was never declared are dropped. A final **global linking pass** shows the model the complete concept inventory and asks for the structural relations that connect concepts which never shared a chunk — the backbone that per-chunk extraction cannot see.

**`clean`** first merges mechanical variants deterministically (casing, accents, plural), then shows the survivors — each annotated with its outgoing relations as evidence — to the model, which proposes a `canonical → aliases` mapping plus a `drop` list for document metadata, incidental example scenarios, and sentence fragments that are not concepts. Canonical names are forced to be existing nodes, so the model cannot invent vocabulary.

**`curate`** groups concepts into thematic domains, flags concepts too generic to be useful as labels, buckets the relations by type, and **breaks cycles** in any relation declared `directed` + `acyclic`. It writes a *draft*. Automatic shaping stops there on purpose: the final pass — draining the `Unclassified` bucket, fixing dubious directions — is manual, because that is where a human is actually cheaper than another LLM call.

## Defining your own relations

### Built-in schemas

`--relations` takes either a built-in name or a path to your own JSON:

| Name | Constant | Keys |
| --- | --- | --- |
| `en` (default) | `DEFAULT_RELATION_SCHEMA_EN` | `prerequisite`, `is_a`, `part_of`, `related_to` |
| `es` | `DEFAULT_RELATION_SCHEMA_ES` | `prerrequisito`, `es_un`, `parte_de`, `relacionado` |

They differ only in what surfaces downstream — `key`, `verbose` and `examples`. The `definition` and `reading` fields stay English in both, because they are embedded in this package's English prompt scaffolding; extraction still preserves the source language either way. Pick `es` when the consumer of the graph renders `details.verbose` into Spanish text, which is exactly what the curated output is for.

`DEFAULT_RELATION_SCHEMA` remains an alias of the English one, so `KnowledgeGraphBuilder()` with no `relations=` is unchanged.

### Your own vocabulary

A relation type carries both its **graph semantics** and its **prompt-facing explanation**:

| Field | Purpose |
| --- | --- |
| `key` | the identifier the model emits, and the bucket name in the output. Single token. |
| `verbose` | human-readable label, written to `details.verbose` in the curated output. |
| `definition` | **shown to the model** — what the relation means, phrased over SOURCE and TARGET. |
| `reading` | **shown to the model** — the sentence that must be true, which pins the direction. |
| `examples` | **shown to the model** — `(source, target)` pairs, rendered as complete triples. |
| `directed` | whether SOURCE and TARGET are interchangeable. |
| `acyclic` | if `directed`, `curate` removes back edges until the relation is a DAG. |
| `use_in_embedding` | carried into the output for downstream consumers; ignored here. |

### In JSON

Copy `examples/spanish_relations.json`, edit, and pass `--relations yourfile.json`:

```json
{
  "fallback": "related_to",
  "types": [
    {
      "key": "causes",
      "verbose": "causes",
      "definition": "the SOURCE brings about, triggers or produces the TARGET.",
      "reading": "SOURCE causes TARGET",
      "examples": [["Insulin resistance", "Type 2 diabetes"]],
      "directed": true,
      "acyclic": true,
      "use_in_embedding": true
    }
  ]
}
```

### In Python

```python
from kg_builder import KnowledgeGraphBuilder, RelationSchema, RelationType

schema = RelationSchema(
    types=(
        RelationType(
            key="causes",
            verbose="causes",
            definition="the SOURCE brings about, triggers or produces the TARGET.",
            reading="SOURCE causes TARGET",
            examples=(("Insulin resistance", "Type 2 diabetes"),),
            acyclic=True,
        ),
        ...
    ),
    fallback="related_to",
)

KnowledgeGraphBuilder(relations=schema).build("corpus")
```

See `examples/custom_schema.py` for a schema that extends a built-in one instead of replacing it.

### `fallback`

The key used when a relation survives validation but its type is not in the schema — which happens when you re-`curate` a graph extracted under a *different* vocabulary. Set it to `None` to drop those relations instead. It also changes the prompt: with a fallback, the model is told to prefer the specific types and reserve the fallback for genuine leftovers; without one, it is told to emit nothing when no type applies.

### Verifying

`kg-builder relations` prints the exact catalog block the prompts embed, plus the graph semantics. Run it after editing — it is the fastest way to confirm the model is being told what you think it is.

## Output formats

**Flat** (`build`, `clean`):

```json
{
  "entities": ["Binary search", "Sorted list"],
  "edges": ["prerequisite"],
  "relations": [["Binary search", "prerequisite", "Sorted list"]]
}
```

**Curated** (`curate`) — relations grouped by type, each group carrying its own semantics:

```json
{
  "concepts_by_domains": {
    "Search algorithms": ["Binary search", "Sorted list"]
  },
  "generic_non_taggable_concepts": ["Algorithm"],
  "relations": [
    {
      "details": {
        "verbose": "has as a prerequisite",
        "directed": true,
        "acyclic": true,
        "use_in_embedding": false
      },
      "relations_data": {
        "Binary search": ["Sorted list"]
      }
    }
  ]
}
```

A consumer of this file should read the relation set from `relations[*].details` rather than hard-coding it — the number and names of relation types are yours to choose.

## Configuration

Every field of `BuilderConfig` has a CLI flag; the defaults are in `kg_builder/config.py`.

| Field | CLI | Default | Notes |
| --- | --- | --- | --- |
| `extraction_model` | `--extraction-model` | `gemma3:27b` | extraction + global linking. Any Ollama tag. |
| `curation_model` | `--curation-model` | `gemma3:27b` | node cleanup + domain curation. |
| `repair_model` | `--repair-model` | `gemma3:4b` | only sees malformed JSON; a small model is enough. |
| `ollama_host` | `--host` | `localhost:11434` | also read from `OLLAMA_HOST`. |
| `request_timeout` | — | `600.0` | seconds; raise it for large chunks on slow hardware. |
| `chunk_size` | `--chunk-size` | `12000` | characters per extraction call. |
| `max_repair_attempts` | — | `3` | JSON repair rounds before giving up on a chunk. |
| `max_evidence_relations` | — | `6` | outgoing relations shown per node during cleanup. |
| `merge_qualifier_pattern` | `--merge-qualifier-pattern` | `None` | regex stripped before comparing names, e.g. `r"\s+in (python\|java)\b"` to merge `Lists in Python` into `Lists`. |
| `plural_suffixes` | — | `("s",)` | suffixes stripped when comparing names. |
| `unclassified_domain` | `--unclassified-domain` | `"Unclassified"` | bucket for concepts the model failed to place. |
| `output_dir` | `--output-dir` | `output` | where the three default filenames land. |

Other flags: `--recursive` (walk subdirectories), `--quiet`, `--no-pull` (skip the model check and warmup).

## Library use

```python
from kg_builder import BuilderConfig, KnowledgeGraphBuilder
from kg_builder.cli import setup_logging

setup_logging()

builder = KnowledgeGraphBuilder(config=BuilderConfig(chunk_size=8_000))
builder.bootstrap()               # reachability check + pull + warmup
builder.build("corpus")
builder.clean()
builder.curate()
```

Nothing is configured on import — no logging sinks, no network calls, and Docling is imported lazily on first conversion. `KnowledgeGraphBuilder(verbose=False)` silences the package's own logging.

All model traffic goes through a single boundary, `kg_builder/inference.py`. To run against something other than Ollama, implement `generate` / `is_available` / `ensure_model` / `warmup` and pass an instance as `engine=`.

## Design notes

Things that look like bugs and are not:

- **Node normalisation is conservative on purpose.** `_norm_key` strips one plural suffix from the end of the whole name, so `Nested lists` and `Nested list` merge but `Nested lists` and `Nested arrays` do not. It does not strip parentheses, to keep `O(n)` and `O(log n)` apart. Over-merging destroys information silently; under-merging is visible in the output and fixable by hand.
- **`clean` runs a deterministic merge before asking the model.** The LLM only ever sees representatives, so it cannot undo a mechanical merge, and its proposal is validated against the existing node set before being applied.
- **Cycle breaking removes the DFS back edge**, not the semantically wrong edge. It guarantees the DAG property for `acyclic` relations; picking which of the two directions is actually correct stays a manual decision.
- **Relations are typed at extraction time**, not by a later classification pass. The model that read the text is the one that knows what the relation meant; asking a second model to type a bag of free-text verbs loses that context.
- **`curate` writes a draft, and stops.** There is no automatic path from `knowledge_graph_autogenerated.json` to a final graph, by design.

## Requirements

Python ≥ 3.10, Ollama reachable, and enough VRAM for the models you configure. Extraction quality tracks model size closely; a 4B model will produce a graph, but not a good one.
